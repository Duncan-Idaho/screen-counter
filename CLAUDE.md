## Architecture

Single-page karaoke score counter, rendered into **one or two browser windows** — see "Projection window" below. Two source files carry essentially all the behavior:

- **`src/stores/game.ts`** — the game state machine and navigation, a Pinia setup store. `screen` (`'setup' | 'round' | 'reveal' | 'total' | 'settings'`) is a store field and `MainScreen.vue` switches on it. Every piece of state (`players`, `currentRound`, `settledRounds`, `revealedIds`, `screen`, `nextPlayerId`, `settingsReturnScreen`, `projectionScreen`) is a `useLocalStorage` ref (VueUse) keyed `screen-counter:*`, so the game auto-persists and auto-restores across reloads with no explicit save/load code. **Appearance state does not live here** — see `src/stores/settings.ts`.
  - **The central invariant is `settledRounds ∈ {currentRound, currentRound + 1}`.** `currentRound` means one thing only: the round the operator is scoring. `settledRounds` means how many rounds are *public*. A round's points are edited straight into `scores[currentRound]` (there is no pending-delta buffer and no commit step), and stay invisible to the audience because `settledRounds` still equals `currentRound`. `endRound()` publishes them with `settledRounds = currentRound + 1` — **settling a round never invents a new one**, which is what keeps `endGame()` idempotent (`max(settledRounds, currentRound + 1)`) with no test on `screen`. Two readings of the totals follow, and mixing them up is the one way to leak scores: `getTotalScore` (everything, round in progress included) is for the **control window only**; `getSettledScore` (public rounds only) is **everything the projection window shows**, on the reveal view as well as the totals view, and is also the sort comparator both of them use. For the same reason `getRevealScore` reads `scores[settledRounds - 1]` rather than `scores[currentRound]`, even though the two are equal during a reveal: `nextRound` moves `currentRound` on, and a projection window receives each changed key as its own `storage` event, so reading `currentRound` would flash a zero across every card in the gap before `projectionScreen` catches up.
  - `openRound()` is the only place `currentRound` ever advances: it steps forward when the current round has already been made public, and resumes it otherwise. `nextRound`, `backToGame` and `resumeGame` all go through it, so none of them can double-advance or strand the operator on an already-revealed round.
  - `sanitizeState()` runs once at store construction to repair whatever came back from localStorage (coerce types, drop nameless/invalid players, clamp `currentRound`, clamp `settledRounds` into `[0, currentRound + 1]`, drop `revealedIds` that match no player, leave `reveal` for `round` when nothing is settled, reset to `setup` when empty). Keep this defensive — persisted data from older versions can be any shape. Note the `settings` screen is deliberately exempt from the reset-to-setup-when-empty rule: it needs no players. Adding a screen means updating **both** the `ScreenName` union and the validation array here.
  - Settings is reachable from every screen, so `openSettings()` records the current screen in `settingsReturnScreen` and `closeSettings()` returns to it (falling back to `setup` when there are no players).
  - `ensureRound(i)` lazily grows every player's `scores` array so index `i` exists; `adjustScore` and `openRound` call it before touching `scores[currentRound]`. Scores are clamped to `MIN_SCORE`/`MAX_SCORE` (0–99), which is why the reveal's "points gained" is never negative.
  - `startGame` resets scores; `resumeGame` keeps them. Both land on `screen = 'round'`.
  - `projectionScreen` (`'round' | 'reveal' | 'total'`, default `'round'`) drives the projection window (below). A `watch(screen, ...)` mirrors `screen` into it for exactly those three values and leaves it alone otherwise, so the audience display never follows the operator into `setup`/`settings`. Being a watcher rather than a line in every action, it's automatically correct no matter which of the 8+ actions changed `screen`.

### Projection window

The operator's controls live on the main route (`/`, `MainScreen.vue`). A button there (round/reveal headers and settings screen) opens a **second browser window** at `/projection` (`ProjectionScreen.vue`) via `window.open` — a read-only mirror with no controls, meant for a second monitor (extended display) facing the audience.

**The projection window is not a mirror of the control window; it is deliberately behind it.** The game runs in three beats:

1. **During a round** the operator tallies points privately (`ScoreGrid mode="tally"`, +/− controls). The projection shows the scoreboard, frozen: every team, carrying the *last settled round's* result and its settled total. Nothing the operator does moves it.
2. **End of round** (`endRound`) settles the round and switches the operator to `ScoreGrid mode="reveal"`: same cards, no +/− controls, each card now a reveal button. The projection's scoreboard **empties**, then gains one card per operator click. Cards sit in settled-score order, so each new one slots in between the teams it now ranks between and the others slide aside to make room — which is the moment a team visibly overtakes another.
3. **Next round** (`nextRound`) opens the next round. Nothing changes on the projection: the scoreboard goes from "all revealed" straight back to "all".

**The in-round and reveal projections are one view with two populations, not two views** — the same `ScoreboardGrid` instance, showing either every player or just `revealedIds`. That is a load-bearing detail, not an optimisation: `ScoreboardCard` animates *on mount*, so remounting the grid between the two would replay every glow and confetti burst at once. Hence `ProjectionScreen` branches on `'total'` first and keeps `'round'`/`'reveal'` in the same `v-else`, and `ScoreboardGrid` passes `animate` (true only while revealing) so the cards that merely sit there — after a reload, or on the way back from the total screen — mount in silence.

Two flows are both supported and equally valid:

- **Two windows**: the operator opens the projection window on a second monitor. `MainScreen` is then purely the control surface; `ProjectionScreen` is the audience-facing display.
- **One window**: the operator never opens a second window (no second monitor, or a mirrored/duplicated display). `MainScreen` alone continues to serve as both control and projection, exactly as the app behaved before this feature — nothing about it changes.

This needed a router (`src/router/index.ts`, `vue-router`, `createWebHashHistory` — `#/projection`, chosen because GitHub Pages has no server-side SPA fallback and `base` is dynamic, see Deployment below) and split what used to be `App.vue`'s single template into: `App.vue` (a thin shell — locale mirroring, `--bg-image`/theme binding, `<router-view>` — kept here because it must apply in *every* window regardless of route), `MainScreen.vue` (the `/` route, today's former `App.vue` content unchanged), and `ProjectionScreen.vue` (the `/projection` route, gated on `game.hasPlayers`/`game.projectionScreen`).

**The order of writes inside an action is load-bearing, not cosmetic.** A projection window receives each changed localStorage key as its own `storage` event, so it renders *every intermediate combination* an action passes through — there is no batching across windows the way Vue batches within one. Two consequences are already baked into `game.ts` and must not be "tidied up":

- `endRound()` writes `revealedIds = []` → `screen = 'reveal'` → `settledRounds`, in that order. Publishing the round before the scoreboard has emptied would flash the entire round's results at the audience one event ahead of the reveal.
- `nextRound()` deliberately does **not** clear `revealedIds` (only `endRound` does). Clearing it there empties the scoreboard for the single event before `projectionScreen` turns back to `'round'`, which reads as every card blinking out and straight back in.

The same hazard is why `getRevealScore` keys off `settledRounds` rather than `currentRound`. When adding an action that writes several keys, walk the intermediate states from the projection's point of view.

**The two windows are fully independent app instances** — `main.ts` runs a second time from scratch in the projection window: its own Pinia, its own `vue-i18n`, its own `document`. There is no direct communication channel between them (no `BroadcastChannel`, no shared memory, no custom event bus). All syncing is the pre-existing `useLocalStorage` + native `storage`-event mechanism already used for every other piece of persisted state — the projection feature adds no new sync machinery, only the `projectionScreen`/`revealedIds` fields a second window happens to read. One consequence worth knowing: `sanitizeState()` only runs once per store instantiation, not reactively on every incoming cross-window `storage` event — a value arriving live in an already-open window relies on write-side invariants (here, the watcher only ever writes `'total'`/`'reveal'`, and `settledRounds` is only ever written as `currentRound + 1`), not a re-validation pass.

- **`src/assets/main.css`** — the layout is the hard part of the UI, not the markup. The app is locked to the viewport (`100dvh`, `overflow: hidden`, no page scroll). Sizing is almost entirely `vmax` / `clamp(px, vmax, px)` so it scales with the larger screen dimension for across-the-room readability. `.score-grid` sizes its columns/rows to the player count: the store exposes `gridMajor`/`gridMinor` (larger/smaller axis, from `rows = ceil(sqrt(n/2))`, `cols = ceil(n/rows)`), `ScoreGrid.vue`/`TotalGrid.vue` pass them as `--grid-major`/`--grid-minor` inline styles, and the CSS maps major→columns / minor→rows in landscape and swaps them under `@media (orientation: portrait)`. `minmax(0, 1fr)` keeps every card inside the locked viewport with no scroll, so large player counts shrink the cards rather than overflow. Card text tracks the card box, not the viewport: `.score-card` is a `container-type: size` query container and its text (`.round-score`, `h3`, `.total-score`, `.grand-total`, etc.) is sized in unclamped `cqmin` units, so it stays proportional as cards shrink and in both orientations. Everything outside the cards still uses `vmax` / `clamp()`; new UI must follow suit — no `rem`. Because the viewport is locked, `.setup-panel` and `.settings-panel` are the only panels allowed `overflow: auto`, since their content is a list that legitimately outgrows a short screen. The total screen's per-round breakdown (`.round-list`) is a value-only grid split into exactly one cell per round via `--round-major`/`--round-minor` (from `roundMajor`/`roundMinor` in the store, same `splitGrid` helper as the player grid, transposed in portrait); each `.round-item` is its own `container-type: size` container so the digit fills its cell in `cqmin` and shrinks automatically as rounds accumulate — every round stays visible, never clipped. `App.vue` sets the background image via a `--bg-image` CSS custom property inline, and the theme overrides ride along the same way (below). The typeface is `--app-font`, defaulted in `:root` and consumed by `.app` as `font-family: var(--app-font), sans-serif` — that declaration is what makes the font themeable at all, since `base.css` puts its stack on `body`, a *parent* of `.app` and so out of reach of the inline overrides; the trailing `sans-serif` is the last resort when a chosen family is not installed. Controls inherit it for free from the existing `font: inherit` rules. `.score-card--readonly` (cards with no +/− buttons: every projection card, and the control's cards once the round is closed) collapses the column normally reserved for `.score-controls`; `.round-panel.no-header`/`.total-panel.no-header` (set by `ProjectionScreen`) collapse the header's grid row so the score grid alone fills the panel. `.scoreboard-grid` is the one layout that is *not* a grid: the reveal empties it and fills it back up one card at a time, so it's a centred `flex-wrap` flow (one card lands dead centre, a partial last row stays centred) whose children take their width/height from the same `--grid-major`/`--grid-minor` the full roster would produce — that's what keeps a card exactly the same size from the first reveal to the last, and it needs its own major/minor swap in the portrait media query since there are no grid tracks to transpose.

The rest is the theming feature:

- **`src/stores/settings.ts`** — appearance + language (background image, theme, font, `locale`), deliberately a **separate** Pinia store from `game.ts` so it never mixes with players and scores. `DEFAULT_THEME` mirrors the palette `main.css` ships in `:root`, so an untouched theme renders identically to before the feature existed. `sanitizeSettings()` mirrors `sanitizeState()`: it rebuilds the theme from `DEFAULT_THEME` (dropping unknown keys from older persisted shapes), falls back per-key on anything `parseColor` rejects, and resets `locale` (`screen-counter:locale`) to `detectBrowserLocale()` when the persisted value is not a `SUPPORTED_LOCALES` member. `locale`'s `useLocalStorage` default is `detectBrowserLocale()`, so the browser language applies until the user picks one on the settings screen; `App.vue` mirrors `settings.locale` onto the `vue-i18n` instance and `document.documentElement.lang` in a `watchEffect`. The `cssVars` getter maps theme keys to the `--app-text` / `--overlay` / … custom property names, and `App.vue` spreads it into the same inline `:style` on `.app` as `--bg-image` — which is why the theme also applies to the settings screen itself, giving a live preview. The font (`screen-counter:font`) is a **scalar setting alongside the theme, not a key inside it** — modeled on `locale`, because a font is not a color and would only fight `parseColor` and the one-`ColorPicker`-per-`THEME_FIELDS` loop. `DEFAULT_FONT` mirrors the `--app-font` default in `:root` for the same reason `DEFAULT_THEME` mirrors the palette, `sanitizeSettings()` repairs it through `normalizeFontFamily` (falling back to `DEFAULT_FONT`), and `cssVars` adds `--app-font` after the theme reduce, so it reaches both windows with no change to `App.vue`. `resetFont()` is deliberately separate from `resetTheme()`: "Reset theme" must not silently change the typeface. Adding a themeable **color** means touching four places in lockstep: `DEFAULT_THEME`, `THEME_FIELDS` (the ordered `ThemeKey[]` that drives the settings UI), `THEME_CSS_VARS`, and the `:root` default in `main.css` — plus a matching `settings.theme.fields.<key>` string in **both** locale catalogs, since `themeFieldLabelKey(key)` derives the i18n key from the theme key.
- **`src/i18n/`** — `locale.ts` is pure (`SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`, `detectBrowserLocale`, `isSupportedLocale`) with no `vue-i18n` import, so `settings.ts` can use it without pulling in the i18n runtime. `index.ts` builds the `createI18n` instance (`legacy: false`) from the YAML catalogs. **All user-facing strings live in `src/i18n/locales/{en,fr}.yaml`** — `@intlify/unplugin-vue-i18n` (wired in `vite.config.ts`) precompiles them at build time, so the runtime-only `vue-i18n` build is enough. `env.d.ts` declares the `*.yaml` module for `vue-tsc`. Every screen component resolves strings through its own `t()` (each installs its own `useI18n({ useScope: 'global' })`, since screens now live in separate components); `ColorPicker.vue` stays i18n-agnostic (it receives an already-resolved `label` string), but `FontPicker.vue` does **not** — it needs a label, a placeholder, a button, a hint and two error states, and threading five resolved strings through props would be worse than the `useI18n` the screens already install.
- **`src/lib/color.ts`**, **`src/lib/font.ts`**, **`src/lib/backgroundImage.ts`** and **`src/lib/localFonts.ts`** — pure/DOM helpers kept out of the stores so the stores stay free of DOM APIs (`FileReader`, `Image`, canvas) and stay testable. `parseColor` returns `null` rather than a fallback so callers own the default. `fileToBackgroundDataUrl` downscales anything over 3 MB to a JPEG so the base64 string stays inside the localStorage quota. `normalizeFontFamily` follows `parseColor`’s contract (`null`, not a fallback) and validates against a **whitelist** rather than a blacklist, because the value ends up in a CSS custom property that `font-family` consumes — it also normalizes (quoting names with spaces, leaving generic families and `-apple-system`-style identifiers bare), so a value round-trips through localStorage unchanged. `localFonts.ts` wraps the Local Font Access API: `queryLocalFonts()` is Chromium-only and needs a secure context plus transient user activation, so it must be called straight from a click handler, and it throws a `LocalFontsError` carrying a typed `reason` (`unsupported` / `denied` / `failed`) so the caller picks an i18n key instead of matching on an English message.
- **`src/components/`** — `MainScreen.vue` (the `/` route: setup/round/reveal/total/settings) and `ProjectionScreen.vue` (the `/projection` route, see "Projection window" above) render player cards through **two separate families, split by window rather than by screen**. Control window: `ScoreGrid.vue` → `ScoreCard.vue`, always in roster order (the operator's cards must never move under their finger) and never animated; its `mode` prop (`'tally' | 'reveal'`) swaps the +/− controls for a whole-card reveal button and swaps `getTotalScore` for `getSettledScore`. Projection window: `ScoreboardGrid.vue` → `ScoreboardCard.vue`, sorted and animated, covering both the in-round and reveal states (above). `TotalGrid.vue` is the projection's end-of-game view and the control's total screen, with a `sorted` prop that is set only by the projection — it is now the only place the per-round breakdown is shown at all. All of them read `useGameStore()` directly rather than taking it as a prop.
  - **Animation lives in `ScoreboardCard` alone, and fires on mount, not on change.** A revealed card appears exactly once, already carrying its result, so there is nothing to diff: `onMounted` puts the glow class on (positive/negative by the sign of the round's points, nothing at all for zero, nothing at all when `animate` is false) and drops it after `REVEAL_HIGHLIGHT_HOLD_MS`. The sequence reads glow → placement (`.scoreboard-enter-*` on the newcomer, `.scoreboard-move` on the cards sliding aside) → confetti (CSS `animation-delay`, held back by `--confetti-delay` until the placement has settled) → both fade out, the last step being the `box-shadow` transition on `.score-card`. Every duration is declared twice, in `src/lib/projectionOrder.ts` and in `main.css`; they must be changed in lockstep. `ColorPicker.vue` is unrelated to any of this: native `<input type="color">` plus an opacity `<input type="range">`, because `<input type="color">` cannot carry alpha and most of the palette is `rgba()` — both inputs rebuild a full `Rgba` from the current value before emitting, so editing the hue keeps the alpha and vice versa. `FontPicker.vue` sits beside it on the settings screen and follows the same emit-only contract, with two deliberate differences. It **commits on `change`, not `input`**: the text input carries a local draft, because writing every keystroke to the store would restyle both windows while a half-typed name matches nothing — only the live preview tracks the draft. And its list of installed families is **rendered rows, not a `<datalist>`**, so each row can be drawn in its own font (the point when hunting for one particular face); the same input doubles as the list filter. The browse button only exists where `canQueryLocalFonts()` is true, and a translated note replaces it everywhere else — free text is the whole feature outside Chromium. Note for tests: `@vue/test-utils`’ `setValue()` fires `input` **and** `change` (for `v-model.lazy`), i.e. a commit — to model typing, set `element.value` and trigger `input` alone.

`App.vue` is presentational infrastructure shared by both routes (locale mirroring, background/theme styling, `<router-view>`) — it no longer contains any screen markup itself; see "Projection window" above for where that went. `src/main.ts` is boilerplate (Pinia + router + i18n + mount).

## Deployment

`.github/workflows/deploy-pages.yml` builds and deploys to GitHub Pages on every push to `main`. `vite.config.ts` derives `base` from `GITHUB_REPOSITORY` when running in Actions (so it serves correctly from `/<repo>/`), and `/` otherwise.

## Conventions

- `@` path alias → `src/`.
- Lint scripts always pass `--fix`; run `npm run lint` and let it rewrite rather than hand-fixing style.
- Store tests (`src/stores/__tests__/*.spec.ts`) clear `localStorage` and call `setActivePinia(createPinia())` in `beforeEach`; persistence is tested by re-creating the pinia instance and reading state back. `useLocalStorage` keeps string refs **raw**, so seed them with `setItem(key, 'settings')`, never `JSON.stringify`.
- Specs must live in a `__tests__` directory: `tsconfig.app.json` excludes that path, `tsconfig.vitest.json` includes it, and `eslint.config.ts` scopes the vitest rules to it. `tsconfig.vitest.json` sets `lib: []`, so newer built-ins (e.g. `Array.prototype.at`) are not typed in tests even though they run fine.
- Vitest `globals` is off — import `describe`/`it`/`expect` explicitly.
