## Architecture

Single-page karaoke score counter, rendered into **one or two browser windows** — see "Projection window" below. Two source files carry essentially all the behavior:

- **`src/stores/game.ts`** — the game state machine and navigation, a Pinia setup store. `screen` (`'setup' | 'round' | 'reveal' | 'total' | 'settings'`) is a store field and `MainScreen.vue` switches on it. Every piece of state (`players`, `currentRound`, `settledRounds`, `revealedIds`, `detailIds`, `screen`, `nextPlayerId`, `settingsReturnScreen`, `projectionScreen`) is a `useLocalStorage` ref (VueUse) keyed `screen-counter:*`, so the game auto-persists and auto-restores across reloads with no explicit save/load code. **Appearance state does not live here** — see `src/stores/settings.ts`.
  - **The central invariant is `settledRounds ∈ {currentRound, currentRound + 1}`.** `currentRound` means one thing only: the round the operator is scoring. `settledRounds` means how many rounds are *public*. A round's points are edited straight into `scores[currentRound]` (there is no pending-delta buffer and no commit step), and stay invisible to the audience because `settledRounds` still equals `currentRound`. `endRound()` publishes them with `settledRounds = currentRound + 1` — **settling a round never invents a new one**, which is what keeps `endGame()` idempotent (`max(settledRounds, currentRound + 1)`) with no test on `screen`. Four readings of the totals follow, and mixing them up is the one way to leak scores: `getTotalScore` (everything, round in progress included) is for the **control window only**; `getSettledScore` (public rounds only) feeds the control's reveal cards and the total view; `getScoreboardScore` (everything before `currentRound`, plus `scores[currentRound]` for a team revealed *during a reveal*) is **the number on every projection scoreboard tile and its sort key** — with `getScoreBeforeRound` as its pre-round half, and **no read of `settledRounds`**, which is what makes `endRound` invisible on the projection whatever the order of its writes; `getFinalScore` (settled minus penalties) is the **only penalty-aware reading**, and belongs to `TotalGrid` alone — for both the number it prints and the order it ranks by. The others must stay penalty-free, or the end-of-game deduction leaks onto the round and reveal screens before the game is over. For the same reason `getRevealScore` reads `scores[settledRounds - 1]` rather than `scores[currentRound]`, even though the two are equal during a reveal: `nextRound` moves `currentRound` on, and a projection window receives each changed key as its own `storage` event, so reading `currentRound` would flash a zero across every card in the gap before `projectionScreen` catches up.
  - **Two reveal lists, one per reveal.** `roundRevealedIds` (`screen-counter:round-revealed`) is the round reveal's: read by the control's `ScoreCard` (`isRoundRevealed`) and by the projection scoreboard (`isRevealedOnScoreboard`, which is true only while `projectionScreen === 'reveal'`, so a stale list is ignored outside a reveal). `revealedIds` is the end-of-game view's, untouched by the scoreboard; `detailIds` (`screen-counter:detail`, always a subset of `revealedIds`, enforced by `sanitizeState`) lists the teams whose per-round detail is open. `revealPlayer` picks the list from `screen` (`reveal` vs `total`). They cannot be merged: `endGame` must empty `revealedIds` before the screen turns over (or the total view mounts with teams already played), and from a reveal that same write would drop already-revealed tiles back to their pre-round total for one `storage` event — and it is indistinguishable from the end of `endRound`. `endRound` empties `roundRevealedIds`; `nextRound` does **not** touch it, and `endGame` empties it **only when `settledRounds <= currentRound`** (the round was never closed, so the list is the previous round's leftover): the final view *reads* the list (`getFinalStartScore` / `getFinalGain`) to know which teams already received the last round's gain at the round reveal, and a stale list would make it skip a gain that was never given. The condition is on state, not on `screen`. The end-of-game view's timing is component-local by design, so nothing about it is persisted and a reload simply lands on the already-settled board.
  - `openRound()` is the only place `currentRound` ever advances: it steps forward when the current round has already been made public, and resumes it otherwise. `nextRound`, `backToGame` and `resumeGame` all go through it, so none of them can double-advance or strand the operator on an already-revealed round.
  - `sanitizeState()` runs once at store construction to repair whatever came back from localStorage (coerce types, drop nameless/invalid players, clamp `currentRound`, clamp `settledRounds` into `[0, currentRound + 1]`, drop `revealedIds` that match no player, default and clamp `penalties` into `[0, 99]`, leave `reveal` for `round` when nothing is settled, reset to `setup` when empty). Keep this defensive — persisted data from older versions can be any shape. **`normalizePlayers` rebuilds each player from an object literal**, which is what drops unknown keys from older shapes — and is also a standing rule for anyone adding a field to `Player`: name it in that literal or it is silently lost on *every* store construction, meaning on every reload and the moment a projection window opens, not just on upgrade. Note the `settings` screen is deliberately exempt from the reset-to-setup-when-empty rule: it needs no players. Adding a screen means updating **both** the `ScreenName` union and the validation array here.
  - Settings is reachable from every screen, so `openSettings()` records the current screen in `settingsReturnScreen` and `closeSettings()` returns to it (falling back to `setup` when there are no players).
  - `ensureRound(i)` lazily grows every player's `scores` array so index `i` exists; `adjustScore` and `openRound` call it before touching `scores[currentRound]`. Scores are clamped to `MIN_SCORE`/`MAX_SCORE` (0–99), which is why the reveal's "points gained" is never negative. **Penalties are a whole-game per-player counter, not a round score**: `adjustPenalty` deliberately never calls `ensureRound` and never reads or writes `scores`, `currentRound` or `settledRounds`, so the central invariant survives every penalty path by construction. They are clamped to `MIN_PENALTY`/`MAX_PENALTY` (0–99) too, but the net `getFinalScore` is allowed to go negative on purpose — clamping it would hide the difference between "penalised to nothing" and "penalised past nothing".
  - `startGame` resets scores and penalties; `resumeGame` keeps both. Both land on `screen = 'round'`. The asymmetry is one line: `resetScores` spreads each player, so `penalties: 0` has to be written **explicitly** there, while `resumeGame` relies on that same spread to preserve them.
  - `projectionScreen` (`'round' | 'reveal' | 'total'`, default `'round'`) drives the projection window (below). A `watch(screen, ...)` mirrors `screen` into it for exactly those three values and leaves it alone otherwise, so the audience display never follows the operator into `setup`/`settings`. Being a watcher rather than a line in every action, it's automatically correct no matter which of the 8+ actions changed `screen`.

### Projection window

The operator's controls live on the main route (`/`, `MainScreen.vue`). A button there (round/reveal headers and settings screen) opens a **second browser window** at `/projection` (`ProjectionScreen.vue`) via `window.open` — a read-only mirror with no controls, meant for a second monitor (extended display) facing the audience.

**The projection window is not a mirror of the control window; it is deliberately behind it.** The game runs in four beats, the last of which is the end of the game:

1. **During a round** the operator tallies points privately (`ScoreGrid mode="tally"`, +/− controls). The projection shows the scoreboard, frozen: every team, **one big number per tile** — its settled total (`getScoreboardScore`) — in settled order. No round points, no "Total" label. Nothing the operator does moves it.
2. **End of round** (`endRound`) switches the operator to `ScoreGrid mode="reveal"`: same cards, no +/− controls, each card a reveal button. **The projection does not change**: tiles stay, still on the pre-round totals and ranks. Each operator click on a card does, on the projection tile, all at once: a green "+N" chip (`gain-chip`, ~2.5 s), the total rolls from the old to the new value (`ScoreRoll`, up this time), and, **once the roll has finished (1.2 s)**, the tile slides to its new rank (a team visibly overtaking another; `ScoreboardGrid` ranks by `getScoreBeforeRound` until that team's own timer of `REVEAL_ROLL_MS` has run, then by `getScoreboardScore`; the finished-roll set is local, never persisted, and seeded synchronously at setup so a reload mid-reveal is silent), and confetti for a positive gain (at 1.8 s, when the slide has landed; `CONFETTI_DELAY_MS = REVEAL_ROLL_MS + REVEAL_MOVE_MS`, equal to `--confetti-delay` in `main.css`). Timeline from the click: chip/roll/glow 0, slide 1.2-1.8 s, confetti 1.8 s, chip gone at 2.5 s, strong glow until 3.2 s. The chips (`gain-chip`) live inside `.score-content` (`position: relative`) so they centre on the number, not on the card. A gain of 0 shows no chip and no roll — the tile is just marked revealed. Every revealed tile keeps a discreet green glow (`score-card--glow`) until `nextRound`.
3. **Next round** (`nextRound`) opens the next round: the glow goes out, nothing else moves (every number is already the settled total). A team the operator skipped jumps to its new total with no chip, roll or confetti — not a leak, the round is over — and slides to its rank.
4. **End of game** (`endGame`) is the **last round's reveal, plus the penalties**, and **the total screen is where it happens** (the last round never gets a round reveal of its own). The projection opens **full**: every team, in its ranking by `getFinalStartScore` (the score from before the last round, plus the last round's gain for a team already revealed at the round reveal), **one number per tile, no breakdown, no "Total" label, no glow** (`TotalGrid sorted revealing`, tiles in `total-card--compact` mode). The control window lists every team as a button in roster order (`TotalGrid selectable`) and always shows the full card. Each click on a team runs a clock of its own, timed from that click (`finalTimeline` in `projectionOrder.ts`, pure and tested): `gain` 0–1.2 s (green "+N" chip, the number rolls up from start to gross); `gained` to 2.5 s (number fixed, chip finishing); `penalty` 2.5–5 s (red "− P" chip, the number rolls down to net); then `settled` — confetti, and the tile **slides, all at once, to its net rank** (`sortByFinalScore`: on a tie on the net, the smaller penalty first). No tile moves before `settled`. A team with no gain starts at `penalty`; with no penalty (none collected, or the setting is off) it settles after the gain; with neither it settles at the click, still with confetti. `gained` exists only so that the second leg of the roll starts from a render where `from === to === gross`. Revealed tiles keep the discreet green glow. A **second click** on a revealed tile (control window) toggles its **detail** (`detailIds`, one id per toggle, so tiles are independent and several can be open to compare): the projection then shows the former `TotalCard` (grand total, per-round chips, penalty chip), but only once that tile is `settled`, so a toggle during the ceremony (the control has no clock) cannot cut the roll short. The control shows revealed tiles with the glow (instead of the old dimming) and open details with an outline and a "Detail shown" badge (`aria-pressed`).


**The in-round and reveal projections are one view with one population** — the same `ScoreboardGrid` instance, always every player. `ProjectionScreen` branches on `'total'` first and keeps `'round'`/`'reveal'` in the same `v-else`, so the tiles are never remounted between round and reveal. Effects hang off the *transition* "not revealed → revealed" (`useRevealEffects`, no `immediate`), never off mount, so a reload or a projection opened mid-reveal shows the current state in silence.

Two flows are both supported and equally valid:

- **Two windows**: the operator opens the projection window on a second monitor. `MainScreen` is then purely the control surface; `ProjectionScreen` is the audience-facing display.
- **One window**: the operator never opens a second window (no second monitor, or a mirrored/duplicated display). `MainScreen` alone continues to serve as both control and projection, exactly as the app behaved before this feature — nothing about it changes.

This needed a router (`src/router/index.ts`, `vue-router`, `createWebHashHistory` — `#/projection`, chosen because GitHub Pages has no server-side SPA fallback and `base` is dynamic, see Deployment below) and split what used to be `App.vue`'s single template into: `App.vue` (a thin shell — locale mirroring, `--bg-image`/theme binding, `<router-view>` — kept here because it must apply in *every* window regardless of route), `MainScreen.vue` (the `/` route, today's former `App.vue` content unchanged), and `ProjectionScreen.vue` (the `/projection` route, gated on `game.hasPlayers`/`game.projectionScreen`).

**The order of writes inside an action is load-bearing, not cosmetic.** A projection window receives each changed localStorage key as its own `storage` event, so it renders *every intermediate combination* an action passes through — there is no batching across windows the way Vue batches within one. Two consequences are already baked into `game.ts` and must not be "tidied up":

- `endRound()` writes `roundRevealedIds = []` → `screen = 'reveal'` → `settledRounds`. The scoreboard number reads `currentRound` (which does not move) and not `settledRounds`, so no intermediate state shows a leaked or a too-low total (`settledRounds` first would leak under the old reading; `screen` first would subtract the wrong round). The list is still emptied first so that, when the projection turns to `'reveal'`, no tile makes a "not revealed → revealed" transition from a stale list (every +N and confetti at once).
- `endGame()` writes `roundRevealedIds = []` (only if the round was never closed, see above) → `detailIds = []` → `revealedIds = []` → `screen = 'total'` → `settledRounds`. The scoreboard ignores the round list outside a reveal, and from a reveal the list is kept, so the frozen scoreboard stays exactly as it is until `projectionScreen` becomes `'total'`. The final view's numbers read `currentRound` only: `getFinalStartScore` = `getScoreBeforeRound` + the last round's score for a team in `roundRevealedIds`, `getFinalGain` = that score for the others, and `start + gain` is always the sum of rounds `0..currentRound` whatever `settledRounds` currently holds — which is why `settledRounds` can land last without any number moving. Both getters are penalty-free. Case A (from the round, points entered): scoreboard `T` → final view `T` in every frame. Case B (from the round, untouched round after `nextRound`): same, no `settledRounds` write, gains are 0. Case C (from the reveal): revealed teams keep `T+G` and get nothing more, the others start at `T` and gain `G` at their click; `settledRounds` is not rewritten. Leaving by `backToGame` is documented rather than fixed: `current-round` arrives before `screen`, so for one frame an unrevealed tile reads `before(r+1)` — exactly what the scoreboard shows next (a skipped team, the round is over). Do not reorder `openRound`; `nextRound` depends on it. `toggleDetail` and `revealPlayer` are one write each, one `storage` event each.
- `nextRound()` writes `current-round` → `players` → `round-themes` → `screen`/`projection-screen`. It does not touch `roundRevealedIds`. A revealed tile's number is `before(r) + G` then `before(r+1) = T+G` plus an empty new score: unchanged at every step; a skipped tile goes `T → T+G` once. The glow and any running chip go out when the projection turns to `'round'`.
- Penalty writes are safe by construction, and the reasoning is worth keeping: `adjustPenalty` touches one ref (`players`), so a projection window gets a single `storage` event and no intermediate state — and on `'round'`/`'reveal'` its output is unchanged anyway, since `ScoreboardCard` reads only the two penalty-free getters. Making the total view penalty-aware likewise adds no flash to `endGame()`, which never writes `players`: the penalties are already in place when that view mounts, so its first frame is already net. Keys that cross windows include `screen-counter:round-revealed` and `screen-counter:penalties-enabled`, read by the projection through `TotalGrid` — toggling it flips the totals live in both windows, the same way a theme colour does.

The same hazard is why `getRevealScore` keys off `settledRounds` rather than `currentRound`. When adding an action that writes several keys, walk the intermediate states from the projection's point of view.

**The two windows are fully independent app instances** — `main.ts` runs a second time from scratch in the projection window: its own Pinia, its own `vue-i18n`, its own `document`. There is no direct communication channel between them (no `BroadcastChannel`, no shared memory, no custom event bus). All syncing is the pre-existing `useLocalStorage` + native `storage`-event mechanism already used for every other piece of persisted state — the projection feature adds no new sync machinery, only the `projectionScreen`/`revealedIds` fields a second window happens to read. One consequence worth knowing: `sanitizeState()` only runs once per store instantiation, not reactively on every incoming cross-window `storage` event — a value arriving live in an already-open window relies on write-side invariants (here, the watcher only ever writes `'total'`/`'reveal'`, and `settledRounds` is only ever written as `currentRound + 1`), not a re-validation pass.

- **`src/assets/main.css`** — the layout is the hard part of the UI, not the markup. The app is locked to the viewport (`100dvh`, `overflow: hidden`, no page scroll). Sizing is almost entirely `vmax` / `clamp(px, vmax, px)` so it scales with the larger screen dimension for across-the-room readability. **No card layout is a CSS grid, on purpose**: a grid packs a partial last row to the start, so five teams would sit 3 + 2 hugging the left edge. `.score-grid` (control tally/reveal screens and both total views) and `.scoreboard-grid` (projection scoreboard) are one shared set of rules — a centred `flex-wrap` flow (`justify-content`/`align-content: center`) whose *children* carry the count: the store exposes `gridMajor`/`gridMinor` (larger/smaller axis, from `rows = ceil(sqrt(n/2))`, `cols = ceil(n/rows)`), `ScoreGrid.vue`/`TotalGrid.vue`/`ScoreboardGrid.vue` pass them as `--grid-major`/`--grid-minor` inline styles, and each card takes `width: calc((100% - gap * (major - 1)) / major)` and the matching height from minor, swapped under `@media (orientation: portrait)` so the larger axis runs down the screen. The wrap then breaks after exactly `major` cards, every card stays inside the locked viewport with no scroll (large player counts shrink the cards rather than overflow), an incomplete last line is centred, and — because the size comes from the *roster* rather than from how many cards are currently shown — a card is exactly the same size whether the scoreboard holds one revealed team or all of them. Card text tracks the card box, not the viewport: `.score-card` is a `container-type: size` query container and its text (`.round-score`, `h3`, `.total-score`, `.grand-total`, etc.) is sized in unclamped `cqmin` units, so it stays proportional as cards shrink and in both orientations. Everything outside the cards still uses `vmax` / `clamp()`; new UI must follow suit — no `rem`. Because the viewport is locked, `.setup-panel` and `.settings-panel` are the only panels allowed `overflow: auto`, since their content is a list that legitimately outgrows a short screen. The total screen's per-round breakdown (`.round-list`) is the same centred wrap one level down — a value-only flow whose chips are sized from `--round-major`/`--round-minor` (computed by `TotalGrid` itself via `splitGrid` in `src/lib/grid.ts`, transposed in portrait — **not** from the store, because the cell count is one per settled round *plus* the optional penalty chip, and whether that chip shows depends on a setting `game.ts` deliberately knows nothing about; `.round-list` clips its overflow, so a split sized for the rounds alone drops the chip silently rather than spilling it) off its own `--round-gap`; each `.round-item` is its own `container-type: size` container so the digit fills its cell in `cqmin` and shrinks automatically as rounds accumulate — every round stays visible, never clipped. `App.vue` sets the background image via a `--bg-image` CSS custom property inline, and the theme overrides ride along the same way (below). The typeface is `--app-font`, defaulted in `:root` and consumed by `.app` as `font-family: var(--app-font), sans-serif` — that declaration is what makes the font themeable at all, since `base.css` puts its stack on `body`, a *parent* of `.app` and so out of reach of the inline overrides; the trailing `sans-serif` is the last resort when a chosen family is not installed. Controls inherit it for free from the existing `font: inherit` rules. `.score-controls` uses `grid-auto-rows: 1fr` rather than fixed tracks, because it holds two buttons or four depending on the penalties setting — explicit tracks would leave empty rows and half-height +/− buttons whenever it is off; `.score-controls--penalty` exists only to shrink the glyph when four rows halve each button's height, and again in portrait, where `cqmin` tracks the card's width while the rows divide its height. `--penalty-text` joins `--button-bg-hover` and friends in the derived-from-the-palette group in `:root`, so the single "Penalty buttons" picker (the `negative` theme key, dead until this feature) themes the control pair, the card's red annotation and the breakdown chip together. `.score-card--readonly` (cards with no +/− buttons: every projection card, and the control's cards once the round is closed) collapses the column normally reserved for `.score-controls`; `.round-panel.no-header`/`.total-panel.no-header` (set by `ProjectionScreen`) collapse the header's grid row so the score grid alone fills the panel. `.scoreboard-grid` adds nothing to the shared layout above but `--confetti-delay`: the centring it already has is what lands the first revealed card dead centre, and the roster-based card size is what keeps it from resizing as the reveal fills up. The end-of-game view adds these to the same file, all of them reusing what is already there: `.score-order-enter-*`/`-leave-*` (the total grid declared only `-move` until that screen became a reveal, so a revealed card would have popped in — a `TransitionGroup` does not run enter transitions on its own initial mount, so an already-full board still renders in one silent shot); `.total-card--compact` (one column: the projection tile before its detail opens), `.gain-chip--penalty` (the same chip as +N in the theme's `negative` colours, reusing `--negative-bg`/`--negative-glow`), `.score-card--detail`/`.detail-badge` (control window); and `.score-roll*`, whose line box is expressed in `em` off `.grand-total`'s `24cqmin` — deliberately not `translateY(-100%)`, since a percentage translate resolves against the track's own height and the track is every line tall.

The rest is the theming feature:

- **`src/stores/settings.ts`** — appearance, language and the one gameplay switch (background image, theme, font, `locale`, `penaltiesEnabled`), deliberately a **separate** Pinia store from `game.ts` so it never mixes with players and scores. `penaltiesEnabled` lives here rather than in `game.ts` for the same reason `locale` does: it is an operator preference that has to survive `startGame`, and `game.ts` is the state machine, not the preference store. It **defaults to on** — an opt-out, not an opt-in — so an operator who wants penalties never has to find the setting first; note the asymmetry that leaves in `sanitizeSettings`, where a *corrupt* persisted value lands on off rather than back on the default, which is the safe direction (show the totals the scores add up to rather than silently deducting). It follows the scalar pattern `locale`/`font` set — its own `useLocalStorage`, a line in `sanitizeSettings`, a setter, an entry in the returned object — and is deliberately **not** a `THEME_FIELDS` key, since it is a boolean rather than a colour. The game store stays ignorant of it: `getFinalScore` always subtracts, and the two components gate the UI. `DEFAULT_THEME` mirrors the palette `main.css` ships in `:root`, so an untouched theme renders identically to before the feature existed. `sanitizeSettings()` mirrors `sanitizeState()`: it rebuilds the theme from `DEFAULT_THEME` (dropping unknown keys from older persisted shapes), falls back per-key on anything `parseColor` rejects, and resets `locale` (`screen-counter:locale`) to `detectBrowserLocale()` when the persisted value is not a `SUPPORTED_LOCALES` member. `locale`'s `useLocalStorage` default is `detectBrowserLocale()`, so the browser language applies until the user picks one on the settings screen; `App.vue` mirrors `settings.locale` onto the `vue-i18n` instance and `document.documentElement.lang` in a `watchEffect`. The `cssVars` getter maps theme keys to the `--app-text` / `--overlay` / … custom property names, and `App.vue` spreads it into the same inline `:style` on `.app` as `--bg-image` — which is why the theme also applies to the settings screen itself, giving a live preview. The font (`screen-counter:font`) is a **scalar setting alongside the theme, not a key inside it** — modeled on `locale`, because a font is not a color and would only fight `parseColor` and the one-`ColorPicker`-per-`THEME_FIELDS` loop. `DEFAULT_FONT` mirrors the `--app-font` default in `:root` for the same reason `DEFAULT_THEME` mirrors the palette, `sanitizeSettings()` repairs it through `normalizeFontFamily` (falling back to `DEFAULT_FONT`), and `cssVars` adds `--app-font` after the theme reduce, so it reaches both windows with no change to `App.vue`. `resetFont()` is deliberately separate from `resetTheme()`: "Reset theme" must not silently change the typeface. Adding a themeable **color** means touching four places in lockstep: `DEFAULT_THEME`, `THEME_FIELDS` (the ordered `ThemeKey[]` that drives the settings UI), `THEME_CSS_VARS`, and the `:root` default in `main.css` — plus a matching `settings.theme.fields.<key>` string in **both** locale catalogs, since `themeFieldLabelKey(key)` derives the i18n key from the theme key.
- **Digits font and projection banner (settings).** `digitFont` (`screen-counter:digit-font`) is a second scalar font setting modeled on `font`, but its default is the **empty string** ("not chosen"): `normalizeFontFamily` rejects `var(...)`, so the fallback cannot be stored and lives in `cssVars`, which always emits `--app-digit-font: <font> || var(--app-font)` inline on `.app`. **Never declare `--app-digit-font: var(--app-font)` in `:root`**: a custom property resolves where it is declared, so it would freeze the default font and never see the operator's choice. **Every game number carries the `.digits` class** (`font-family: var(--app-digit-font), sans-serif`) — scores, totals, chips, `ScoreRoll`, the round number; any new displayed number must too. Strings mixing words and a number (`round.total`, `round.title`, `reveal.title`) go through `LabeledNumber.vue` (`<i18n-t>` with an `#n` slot), so only the number takes the digits font. `FontPicker` has a `variant: 'text' | 'digits'` prop. `bannerHeight` (`screen-counter:banner-height`, 10–50, default 33, `clampBannerHeight`) reaches the projection as `--projection-banner-height` in `dvh`; `.projection-round-panel` gives that height to `.projection-banner` (a `container-type: size` box whose title/theme font sizes are `cq*` units bound by height and by character count via `--chars`). The banner replaces the projection's round/reveal header and shows "Round N" in both views; the total view has none. The control window keeps its own header.
- **`src/i18n/`** — `locale.ts` is pure (`SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`, `detectBrowserLocale`, `isSupportedLocale`) with no `vue-i18n` import, so `settings.ts` can use it without pulling in the i18n runtime. `index.ts` builds the `createI18n` instance (`legacy: false`) from the YAML catalogs. **All user-facing strings live in `src/i18n/locales/{en,fr}.yaml`** — `@intlify/unplugin-vue-i18n` (wired in `vite.config.ts`) precompiles them at build time, so the runtime-only `vue-i18n` build is enough. `env.d.ts` declares the `*.yaml` module for `vue-tsc`. Every screen component resolves strings through its own `t()` (each installs its own `useI18n({ useScope: 'global' })`, since screens now live in separate components); `ColorPicker.vue` stays i18n-agnostic (it receives an already-resolved `label` string), but `FontPicker.vue` does **not** — it needs a label, a placeholder, a button, a hint and two error states, and threading five resolved strings through props would be worse than the `useI18n` the screens already install.
- **`src/lib/color.ts`**, **`src/lib/font.ts`**, **`src/lib/grid.ts`**, **`src/lib/backgroundImage.ts`** and **`src/lib/localFonts.ts`** — pure/DOM helpers kept out of the stores so the stores stay free of DOM APIs (`FileReader`, `Image`, canvas) and stay testable. `parseColor` returns `null` rather than a fallback so callers own the default. `grid.ts` holds `splitGrid`, which used to live inside the game store; it moved out so both the store (player cards, from the roster) and `TotalGrid` (the breakdown, whose cell count depends on a setting the store must not know) can call the same function. `fileToBackgroundDataUrl` downscales anything over 3 MB to a JPEG so the base64 string stays inside the localStorage quota. `normalizeFontFamily` follows `parseColor`’s contract (`null`, not a fallback) and validates against a **whitelist** rather than a blacklist, because the value ends up in a CSS custom property that `font-family` consumes — it also normalizes (quoting names with spaces, leaving generic families and `-apple-system`-style identifiers bare), so a value round-trips through localStorage unchanged. `localFonts.ts` wraps the Local Font Access API: `queryLocalFonts()` is Chromium-only and needs a secure context plus transient user activation, so it must be called straight from a click handler, and it throws a `LocalFontsError` carrying a typed `reason` (`unsupported` / `denied` / `failed`) so the caller picks an i18n key instead of matching on an English message.
- **`src/components/`** — `MainScreen.vue` (the `/` route: setup/round/reveal/total/settings) and `ProjectionScreen.vue` (the `/projection` route, see "Projection window" above) render player cards through **two separate families, split by window rather than by screen**. Control window: `ScoreGrid.vue` → `ScoreCard.vue`, always in roster order (the operator's cards must never move under their finger) and never animated; its `mode` prop (`'tally' | 'reveal'`) swaps the +/− controls for a whole-card reveal button and swaps `getTotalScore` for `getSettledScore`. In `tally` mode with penalties on it carries **three** numbers and **four** controls: the round draft, the still-gross total, a red penalty annotation beside it, and a second +/− pair below the first. Both pairs use the same two glyphs, so colour and the heavier rule between them are the only visual difference — which is what makes all four `aria-label`s load-bearing rather than decoration. The `reveal` card stays deliberately penalty-free: it shows the round's gain and the settled total (the projection shows a single number per tile). Projection window: `ScoreboardGrid.vue` → `ScoreboardCard.vue`, sorted by `getScoreboardScore`, covering both the in-round and reveal states (above). `TotalGrid.vue` → `TotalCard.vue` (→ `ScoreRoll.vue`) is the projection's end-of-game view and the control's total screen — the only place the per-round breakdown is shown at all, and, being the end of the game, the only view where penalties apply, as a red chip after the round chips and as the **net** total it both prints and ranks by — through `sortByFinalScore` rather than the scoreboard's `sortByTotalScore`, because a tie on the net is broken by the **smaller** penalty (37−7 and 38−8 both come to 30, and the team that lost less to penalties places higher). Both keys are read at the card's current phase, so a team still mid-ceremony ties as though it had no penalty: ranking it by a deduction the audience has not been shown yet would seat it low with nothing to explain why. Because that screen is also the end-of-game view, it has **three independent props named for what they do rather than for the window that sets them**: `sorted` (rank the cards), `revealing` (run the per-team clock and show compact tiles until a team is settled — it no longer filters the population, which is always the whole roster) and `selectable` (the whole card is a button: reveal, then toggle the detail). Only two combinations exist today — `<TotalGrid selectable />` on the control and `<TotalGrid sorted revealing />` on the projection — but keeping them separate is what stops a future "sort the control window too" from silently switching the buttons off. `TotalCard` takes its numbers already resolved (`start`, `gain`, `roundScores`, `penalty`, `detail`; gross is `start + gain`, never summed from `roundScores`, which depends on `settledRounds`), so whether penalties are enabled at all stays `TotalGrid`'s business and `penalty === 0` simply means "no chip". All of them read `useGameStore()` directly rather than taking it as a prop; `ScoreCard` and `TotalGrid` read `useSettingsStore()` the same way, to gate the penalty UI.
  - **The round reveal's animation lives in `ScoreboardCard` and `useRevealEffects` (`src/composables/`), and fires on the transition, not on mount.** The composable takes two getters (`revealed`, `gain`) and knows neither store nor rounds, so the end-of-game view can reuse it. It owns the "+N" chip (`REVEAL_GAIN_CHIP_MS`) and the celebration (strong glow + confetti, `REVEAL_HIGHLIGHT_HOLD_MS`); both are cancelled when `revealed` flips again. The tile's single number is a `ScoreRoll` with `:key="from"` (`from = getScoreBeforeRound`, `to = getScoreboardScore`): an unrevealed tile has `from === to`, so the new total is not even in the DOM; on a click `to` changes on the same element, so the CSS transition runs; on `nextRound` `from` changes, the roll remounts and shows the total with no scroll. `.score-card--glow` (persistent, discreet), `.gain-chip` and `.scoreboard-total` are generic, scoreboard-free names. Durations are declared twice, in `src/lib/projectionOrder.ts` and in `main.css` (`REVEAL_ROLL_MS`, `REVEAL_GAIN_CHIP_MS`, `CONFETTI_*`, `REVEAL_HIGHLIGHT_HOLD_MS`); change them in lockstep. `.score-card--negative` is gone (a gain is never negative).
  - **Roll regressions (#28), two rules to keep.** (1) `ScoreRoll`'s track is never `position: absolute`: it contributes no width and the shrink-wrapped tile collapsed to 0px, hiding every digit in the final view. `highOnTop` anchors through the window instead (`.score-roll--bottom` is a flex column with `justify-content: flex-end`, so a gain's tall track grows upwards around its bottom line; the percentage transform then differs from the idle one, which is what lets the roll run). (2) `ScoreboardGrid` renders tiles in roster order and ranks them with CSS `order`; `ScoreboardCard` hands the roll its new `to` one animation frame late. A tile that overtakes another is measured and translated by `TransitionGroup` in the same flush that changes `to`, and the track's CSS transition did not survive that (the total jumped). Keep both.
  - **The end-of-game clock is the one deliberate exception: it lives in `TotalGrid`, not in `TotalCard`.** The reorder is a *grid* concern — a team is ranked by its start score until its clock reaches `settled` and by its net score after (`rankOf`; `tiebreakOf` reads 0 until then), and that late switch of the sort key is what makes the tile slide to its net rank. So the grid keeps a per-id `FinalPhase` map (`'idle' | 'gain' | 'gained' | 'penalty' | 'settled'`), seeded **synchronously at setup** (ids already revealed when it mounts — a reload, or a projection window opened mid-ceremony — start settled and therefore silent, detail included), with `'idle'` as the fallback; the watcher on `revealedIds` walks `finalTimeline(gain, penalty)` with timers. It does not use `useRevealEffects` (that fires chip and confetti on one transition; here they are two instants separated by the penalty step): the chips are derived from the phase. The card keys its confetti off the *transition* into `'settled'` rather than the value — the same transition-not-mount principle as `useRevealEffects`. `ScoreRoll.vue` is the odometer (in the final view, `high-on-top`: the column always lists the highest value first; a gain rests on the bottom line and slides down to the top one, a penalty rests on the top line and slides up � track anchored `--bottom`/`--top`, offset in `--roll-offset`; the round reveal keeps the default from-to order and `--roll-index`), timed by a **CSS transition, not JS** (`REVEAL_ROLL_MS`, 1.2 s for every roll) — a transition never fires for a value present at first paint, so every "should be silent" case is silent by construction. During the ceremony its key is `rollFrom`, constant, so `to` changes on the same element; once settled it is `gross-net`, so toggling the penalties setting snaps instead of scrolling. `ColorPicker.vue` is unrelated to any of this: native `<input type="color">` plus an opacity `<input type="range">`, because `<input type="color">` cannot carry alpha and most of the palette is `rgba()` — both inputs rebuild a full `Rgba` from the current value before emitting, so editing the hue keeps the alpha and vice versa. `FontPicker.vue` sits beside it on the settings screen and follows the same emit-only contract, with two deliberate differences. It **commits on `change`, not `input`**: the text input carries a local draft, because writing every keystroke to the store would restyle both windows while a half-typed name matches nothing — only the live preview tracks the draft. And its list of installed families is **rendered rows, not a `<datalist>`**, so each row can be drawn in its own font (the point when hunting for one particular face); the same input doubles as the list filter. The browse button only exists where `canQueryLocalFonts()` is true, and a translated note replaces it everywhere else — free text is the whole feature outside Chromium. Note for tests: `@vue/test-utils`’ `setValue()` fires `input` **and** `change` (for `v-model.lazy`), i.e. a commit — to model typing, set `element.value` and trigger `input` alone.

`App.vue` is presentational infrastructure shared by both routes (locale mirroring, background/theme styling, `<router-view>`) — it no longer contains any screen markup itself; see "Projection window" above for where that went. `src/main.ts` is boilerplate (Pinia + router + i18n + mount).

## Deployment

`.github/workflows/deploy-pages.yml` builds and deploys to GitHub Pages on every push to `main` **or** `beta` (and `workflow_dispatch`). GitHub Pages allows one deployment per repository, so each run checks out both branches, builds `main` into the site root and `beta` (with `APP_CHANNEL=beta`) into `beta/`, and uploads a single artifact. If no `beta` branch exists, only the stable version is deployed. `vite.config.ts` derives `base` from `GITHUB_REPOSITORY` when running in Actions (so it serves correctly from `/<repo>/`), and `/` otherwise; the beta channel appends `beta/` (`/<repo>/beta/` or `/beta/`).

## Parallel versions (stable / beta)

| | Branch | URL |
|---|---|---|
| Stable | `main` | `https://duncan-idaho.github.io/screen-counter/` |
| Beta | `beta` | `https://duncan-idaho.github.io/screen-counter/beta/` |

Feature branches are merged by PR into `beta`. `main` only receives urgent stable fixes and the beta once the client has validated it.

- **`APP_CHANNEL`** (`stable` default, or `beta`) is read by `vite.config.ts`; it sets `base` and defines `import.meta.env.VITE_APP_CHANNEL`. `vite build --mode beta` is equivalent, which is what `npm run build:beta` uses (type-check + beta build, output in `dist/`; `npm run dev -- --mode beta` runs the dev server as beta).
- **Storage prefix.** `localStorage` is shared per origin, not per path, so stable and beta would otherwise share keys. `src/lib/storageKey.ts` exposes `storageKey(name)`: `screen-counter:<name>` in stable (**unchanged**, existing customer data is preserved), `screen-counter-beta:<name>` in beta. **Every new localStorage key must go through `storageKey()`** — never write a `'screen-counter:...'` literal. The projection window name (`PROJECTION_WINDOW_NAME`) is per channel too, so a beta projection never reuses the stable one. Beta data is not migrated to stable.
- **Beta aids.** `App.vue` (present in every window) shows a small translucent `BÊTA`/`BETA` badge (`.beta-badge`, click-through) and suffixes the tab title (`Screen Counter (beta)`) only when `IS_BETA`.
- **Promotion process.** (1) The client validates the beta at `/beta/`. (2) PR `beta` → `main`. (3) The next deployment publishes it at the root. (4) Resynchronise `beta` on `main` (e.g. `git checkout beta && git merge main`, or reset it to `main`) for the next cycle.

## Conventions

- `@` path alias → `src/`.
- Lint scripts always pass `--fix`; run `npm run lint` and let it rewrite rather than hand-fixing style.
- Store tests (`src/stores/__tests__/*.spec.ts`) clear `localStorage` and call `setActivePinia(createPinia())` in `beforeEach`; persistence is tested by re-creating the pinia instance and reading state back. `useLocalStorage` keeps string refs **raw**, so seed them with `setItem(key, 'settings')`, never `JSON.stringify`.
- Specs must live in a `__tests__` directory: `tsconfig.app.json` excludes that path, `tsconfig.vitest.json` includes it, and `eslint.config.ts` scopes the vitest rules to it. `tsconfig.vitest.json` sets `lib: []`, so newer built-ins (e.g. `Array.prototype.at`) are not typed in tests even though they run fine.
- Vitest `globals` is off — import `describe`/`it`/`expect` explicitly.
