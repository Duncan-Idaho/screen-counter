## Architecture

Single-page karaoke score counter, rendered into **one or two browser windows** — see "Projection window" below. Two source files carry essentially all the behavior:

- **`src/stores/game.ts`** — the game state machine and navigation, a Pinia setup store. `screen` (`'setup' | 'round' | 'total' | 'settings'`) is a store field and `MainScreen.vue` switches on it. Every piece of state (`players`, `currentRound`, `screen`, `nextPlayerId`, `settingsReturnScreen`, `projectionScreen`) is a `useLocalStorage` ref (VueUse) keyed `screen-counter:*`, so the game auto-persists and auto-restores across reloads with no explicit save/load code. **Appearance state does not live here** — see `src/stores/settings.ts`.
  - `sanitizeState()` runs once at store construction to repair whatever came back from localStorage (coerce types, drop nameless/invalid players, clamp `currentRound`, reset to `setup` when empty). Keep this defensive — persisted data from older versions can be any shape. Note the `settings` screen is deliberately exempt from the reset-to-setup-when-empty rule: it needs no players. Adding a screen means updating **both** the `ScreenName` union and the validation array here.
  - Settings is reachable from every screen, so `openSettings()` records the current screen in `settingsReturnScreen` and `closeSettings()` returns to it (falling back to `setup` when there are no players).
  - `ensureRound(i)` lazily grows every player's `scores` array so index `i` exists; increment/decrement/nextRound all call it before touching `scores[currentRound]`. Scores are clamped to `MIN_SCORE`/`MAX_SCORE` (0–99).
  - `startGame` resets scores; `resumeGame` keeps them. Both just set `screen = 'round'`.
  - `projectionScreen` (`'round' | 'total'`, default `'round'`) drives the projection window (below). A `watch(screen, ...)` mirrors `screen` into it whenever `screen` becomes `'round'` or `'total'`, and leaves it alone otherwise — so it's automatically correct no matter which of the 7+ actions changed `screen`, with no risk of a future one forgetting to update it.

### Projection window

The operator's controls live on the main route (`/`, `MainScreen.vue`). A button there (round-screen header and settings screen) opens a **second browser window** at `/projection` (`ProjectionScreen.vue`) via `window.open` — a read-only mirror with no controls, meant for a second monitor (extended display) facing the audience. Two flows are both supported and equally valid:

- **Two windows**: the operator opens the projection window on a second monitor. `MainScreen` is then purely the control surface; `ProjectionScreen` is the audience-facing display.
- **One window**: the operator never opens a second window (no second monitor, or a mirrored/duplicated display). `MainScreen` alone continues to serve as both control and projection, exactly as the app behaved before this feature — nothing about it changes.

This needed a router (`src/router/index.ts`, `vue-router`, `createWebHashHistory` — `#/projection`, chosen because GitHub Pages has no server-side SPA fallback and `base` is dynamic, see Deployment below) and split what used to be `App.vue`'s single template into: `App.vue` (a thin shell — locale mirroring, `--bg-image`/theme binding, `<router-view>` — kept here because it must apply in *every* window regardless of route), `MainScreen.vue` (the `/` route, today's former `App.vue` content unchanged), and `ProjectionScreen.vue` (the `/projection` route, gated on `game.hasPlayers`/`game.projectionScreen`).

**The two windows are fully independent app instances** — `main.ts` runs a second time from scratch in the projection window: its own Pinia, its own `vue-i18n`, its own `document`. There is no direct communication channel between them (no `BroadcastChannel`, no shared memory, no custom event bus). All syncing is the pre-existing `useLocalStorage` + native `storage`-event mechanism already used for every other piece of persisted state — the projection feature adds no new sync machinery, only the `projectionScreen` field a second window happens to read. One consequence worth knowing: `sanitizeState()` only runs once per store instantiation, not reactively on every incoming cross-window `storage` event — a value arriving live in an already-open window relies on write-side invariants (here, the watcher only ever writes `'round'`/`'total'`), not a re-validation pass.

- **`src/assets/main.css`** — the layout is the hard part of the UI, not the markup. The app is locked to the viewport (`100dvh`, `overflow: hidden`, no page scroll). Sizing is almost entirely `vmax` / `clamp(px, vmax, px)` so it scales with the larger screen dimension for across-the-room readability. `.score-grid` sizes its columns/rows to the player count: the store exposes `gridMajor`/`gridMinor` (larger/smaller axis, from `rows = ceil(sqrt(n/2))`, `cols = ceil(n/rows)`), `ScoreGrid.vue`/`TotalGrid.vue` pass them as `--grid-major`/`--grid-minor` inline styles, and the CSS maps major→columns / minor→rows in landscape and swaps them under `@media (orientation: portrait)`. `minmax(0, 1fr)` keeps every card inside the locked viewport with no scroll, so large player counts shrink the cards rather than overflow. Card text tracks the card box, not the viewport: `.score-card` is a `container-type: size` query container and its text (`.round-score`, `h3`, `.total-score`, `.grand-total`, etc.) is sized in unclamped `cqmin` units, so it stays proportional as cards shrink and in both orientations. Everything outside the cards still uses `vmax` / `clamp()`; new UI must follow suit — no `rem`. Because the viewport is locked, `.setup-panel` and `.settings-panel` are the only panels allowed `overflow: auto`, since their content is a list that legitimately outgrows a short screen. The total screen's per-round breakdown (`.round-list`) is a value-only grid split into exactly one cell per round via `--round-major`/`--round-minor` (from `roundMajor`/`roundMinor` in the store, same `splitGrid` helper as the player grid, transposed in portrait); each `.round-item` is its own `container-type: size` container so the digit fills its cell in `cqmin` and shrinks automatically as rounds accumulate — every round stays visible, never clipped. `App.vue` sets the background image via a `--bg-image` CSS custom property inline, and the theme overrides ride along the same way (below). `.score-card--readonly` (set by `ScoreGrid` when `interactive: false`) collapses the column normally reserved for `.score-controls`; `.round-panel.no-header`/`.total-panel.no-header` (set by `ProjectionScreen`) collapse the header's grid row so the score grid alone fills the panel.

The rest is the theming feature:

- **`src/stores/settings.ts`** — appearance + language (background image, theme, `locale`), deliberately a **separate** Pinia store from `game.ts` so it never mixes with players and scores. `DEFAULT_THEME` mirrors the palette `main.css` ships in `:root`, so an untouched theme renders identically to before the feature existed. `sanitizeSettings()` mirrors `sanitizeState()`: it rebuilds the theme from `DEFAULT_THEME` (dropping unknown keys from older persisted shapes), falls back per-key on anything `parseColor` rejects, and resets `locale` (`screen-counter:locale`) to `detectBrowserLocale()` when the persisted value is not a `SUPPORTED_LOCALES` member. `locale`'s `useLocalStorage` default is `detectBrowserLocale()`, so the browser language applies until the user picks one on the settings screen; `App.vue` mirrors `settings.locale` onto the `vue-i18n` instance and `document.documentElement.lang` in a `watchEffect`. The `cssVars` getter maps theme keys to the `--app-text` / `--overlay` / … custom property names, and `App.vue` spreads it into the same inline `:style` on `.app` as `--bg-image` — which is why the theme also applies to the settings screen itself, giving a live preview. Adding a themeable color means touching four places in lockstep: `DEFAULT_THEME`, `THEME_FIELDS` (the ordered `ThemeKey[]` that drives the settings UI), `THEME_CSS_VARS`, and the `:root` default in `main.css` — plus a matching `settings.theme.fields.<key>` string in **both** locale catalogs, since `themeFieldLabelKey(key)` derives the i18n key from the theme key.
- **`src/i18n/`** — `locale.ts` is pure (`SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`, `detectBrowserLocale`, `isSupportedLocale`) with no `vue-i18n` import, so `settings.ts` can use it without pulling in the i18n runtime. `index.ts` builds the `createI18n` instance (`legacy: false`) from the YAML catalogs. **All user-facing strings live in `src/i18n/locales/{en,fr}.yaml`** — `@intlify/unplugin-vue-i18n` (wired in `vite.config.ts`) precompiles them at build time, so the runtime-only `vue-i18n` build is enough. `env.d.ts` declares the `*.yaml` module for `vue-tsc`. Every screen component resolves strings through its own `t()` (each installs its own `useI18n({ useScope: 'global' })`, since screens now live in separate components); `ColorPicker.vue` stays i18n-agnostic (it receives an already-resolved `label` string).
- **`src/lib/color.ts`** and **`src/lib/backgroundImage.ts`** — pure/DOM helpers kept out of the stores so the stores stay free of DOM APIs (`FileReader`, `Image`, canvas) and stay testable. `parseColor` returns `null` rather than a fallback so callers own the default. `fileToBackgroundDataUrl` downscales anything over 3 MB to a JPEG so the base64 string stays inside the localStorage quota.
- **`src/components/`** — `MainScreen.vue` (the `/` route: setup/round/total/settings, unchanged from the pre-router `App.vue`) and `ProjectionScreen.vue` (the `/projection` route, see "Projection window" above) both render player scores via two shared presentational components: `ScoreGrid.vue` (round-view grid; `interactive` prop toggles the `.score-content` click target and `.score-controls` +/- buttons on or off) and `TotalGrid.vue` (total-view grid; no interactive variant, since that grid has never had controls). Both read `useGameStore()` directly rather than taking it as a prop. `ColorPicker.vue` is unrelated to any of this: native `<input type="color">` plus an opacity `<input type="range">`, because `<input type="color">` cannot carry alpha and most of the palette is `rgba()` — both inputs rebuild a full `Rgba` from the current value before emitting, so editing the hue keeps the alpha and vice versa.

`App.vue` is presentational infrastructure shared by both routes (locale mirroring, background/theme styling, `<router-view>`) — it no longer contains any screen markup itself; see "Projection window" above for where that went. `src/main.ts` is boilerplate (Pinia + router + i18n + mount).

## Deployment

`.github/workflows/deploy-pages.yml` builds and deploys to GitHub Pages on every push to `main`. `vite.config.ts` derives `base` from `GITHUB_REPOSITORY` when running in Actions (so it serves correctly from `/<repo>/`), and `/` otherwise.

## Conventions

- `@` path alias → `src/`.
- Lint scripts always pass `--fix`; run `npm run lint` and let it rewrite rather than hand-fixing style.
- Store tests (`src/stores/__tests__/*.spec.ts`) clear `localStorage` and call `setActivePinia(createPinia())` in `beforeEach`; persistence is tested by re-creating the pinia instance and reading state back. `useLocalStorage` keeps string refs **raw**, so seed them with `setItem(key, 'settings')`, never `JSON.stringify`.
- Specs must live in a `__tests__` directory: `tsconfig.app.json` excludes that path, `tsconfig.vitest.json` includes it, and `eslint.config.ts` scopes the vitest rules to it. `tsconfig.vitest.json` sets `lib: []`, so newer built-ins (e.g. `Array.prototype.at`) are not typed in tests even though they run fine.
- Vitest `globals` is off — import `describe`/`it`/`expect` explicitly.
