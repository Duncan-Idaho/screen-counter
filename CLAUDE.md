## Architecture

Single-page karaoke score counter, rendered into **one or two browser windows** — see "Projection window" below. Two source files carry essentially all the behavior:

- **`src/stores/game.ts`** — the game state machine and navigation, a Pinia setup store. `screen` (`'setup' | 'round' | 'reveal' | 'total' | 'settings'`) is a store field and `MainScreen.vue` switches on it. Every piece of state (`players`, `currentRound`, `settledRounds`, `revealedIds`, `screen`, `nextPlayerId`, `settingsReturnScreen`, `projectionScreen`) is a `useLocalStorage` ref (VueUse) keyed `screen-counter:*`, so the game auto-persists and auto-restores across reloads with no explicit save/load code. **Appearance state does not live here** — see `src/stores/settings.ts`.
  - **The central invariant is `settledRounds ∈ {currentRound, currentRound + 1}`.** `currentRound` means one thing only: the round the operator is scoring. `settledRounds` means how many rounds are *public*. A round's points are edited straight into `scores[currentRound]` (there is no pending-delta buffer and no commit step), and stay invisible to the audience because `settledRounds` still equals `currentRound`. `endRound()` publishes them with `settledRounds = currentRound + 1` — **settling a round never invents a new one**, which is what keeps `endGame()` idempotent (`max(settledRounds, currentRound + 1)`) with no test on `screen`. Three readings of the totals follow, and mixing them up is the one way to leak scores: `getTotalScore` (everything, round in progress included) is for the **control window only**; `getSettledScore` (public rounds only) is **everything the projection window shows** during a round and a reveal, and is the sort comparator the scoreboard uses; `getFinalScore` (settled minus penalties) is the **only penalty-aware reading**, and belongs to `TotalGrid` alone — for both the number it prints and the order it ranks by. The other two must stay penalty-free, or the end-of-game deduction leaks onto the round and reveal screens before the game is over. For the same reason `getRevealScore` reads `scores[settledRounds - 1]` rather than `scores[currentRound]`, even though the two are equal during a reveal: `nextRound` moves `currentRound` on, and a projection window receives each changed key as its own `storage` event, so reading `currentRound` would flash a zero across every card in the gap before `projectionScreen` catches up.
  - `revealedIds` serves **both** reveals — the round one and the end-of-game one — because they can never overlap: `revealPlayer` accepts clicks on the `reveal` and `total` screens only, and `endRound`/`endGame` each empty the list on the way in. The end-of-game reveal needs no state of its own beyond that; the ceremony's timing is component-local by design, so nothing about it is persisted and a reload simply lands on the already-settled board.
  - `openRound()` is the only place `currentRound` ever advances: it steps forward when the current round has already been made public, and resumes it otherwise. `nextRound`, `backToGame` and `resumeGame` all go through it, so none of them can double-advance or strand the operator on an already-revealed round.
  - `sanitizeState()` runs once at store construction to repair whatever came back from localStorage (coerce types, drop nameless/invalid players, clamp `currentRound`, clamp `settledRounds` into `[0, currentRound + 1]`, drop `revealedIds` that match no player, default and clamp `penalties` into `[0, 99]`, leave `reveal` for `round` when nothing is settled, reset to `setup` when empty). Keep this defensive — persisted data from older versions can be any shape. **`normalizePlayers` rebuilds each player from an object literal**, which is what drops unknown keys from older shapes — and is also a standing rule for anyone adding a field to `Player`: name it in that literal or it is silently lost on *every* store construction, meaning on every reload and the moment a projection window opens, not just on upgrade. Note the `settings` screen is deliberately exempt from the reset-to-setup-when-empty rule: it needs no players. Adding a screen means updating **both** the `ScreenName` union and the validation array here.
  - Settings is reachable from every screen, so `openSettings()` records the current screen in `settingsReturnScreen` and `closeSettings()` returns to it (falling back to `setup` when there are no players).
  - `ensureRound(i)` lazily grows every player's `scores` array so index `i` exists; `adjustScore` and `openRound` call it before touching `scores[currentRound]`. Scores are clamped to `MIN_SCORE`/`MAX_SCORE` (0–99), which is why the reveal's "points gained" is never negative. **Penalties are a whole-game per-player counter, not a round score**: `adjustPenalty` deliberately never calls `ensureRound` and never reads or writes `scores`, `currentRound` or `settledRounds`, so the central invariant survives every penalty path by construction. They are clamped to `MIN_PENALTY`/`MAX_PENALTY` (0–99) too, but the net `getFinalScore` is allowed to go negative on purpose — clamping it would hide the difference between "penalised to nothing" and "penalised past nothing".
  - `startGame` resets scores and penalties; `resumeGame` keeps both. Both land on `screen = 'round'`. The asymmetry is one line: `resetScores` spreads each player, so `penalties: 0` has to be written **explicitly** there, while `resumeGame` relies on that same spread to preserve them.
  - `projectionScreen` (`'round' | 'reveal' | 'total'`, default `'round'`) drives the projection window (below). A `watch(screen, ...)` mirrors `screen` into it for exactly those three values and leaves it alone otherwise, so the audience display never follows the operator into `setup`/`settings`. Being a watcher rather than a line in every action, it's automatically correct no matter which of the 8+ actions changed `screen`.

### Projection window

The operator's controls live on the main route (`/`, `MainScreen.vue`). A button there (round/reveal headers and settings screen) opens a **second browser window** at `/projection` (`ProjectionScreen.vue`) via `window.open` — a read-only mirror with no controls, meant for a second monitor (extended display) facing the audience.

**The projection window is not a mirror of the control window; it is deliberately behind it.** The game runs in four beats, the last of which is the end of the game:

1. **During a round** the operator tallies points privately (`ScoreGrid mode="tally"`, +/− controls). The projection shows the scoreboard, frozen: every team, carrying the *last settled round's* result and its settled total. Nothing the operator does moves it.
2. **End of round** (`endRound`) settles the round and switches the operator to `ScoreGrid mode="reveal"`: same cards, no +/− controls, each card now a reveal button. The projection's scoreboard **empties**, then gains one card per operator click. Cards sit in settled-score order, so each new one slots in between the teams it now ranks between and the others slide aside to make room — which is the moment a team visibly overtakes another.
3. **Next round** (`nextRound`) opens the next round. Nothing changes on the projection: the scoreboard goes from "all revealed" straight back to "all".
4. **End of game** (`endGame`) is a second reveal, over the final scores instead of one round's points, and **the total screen is where it happens** — "every card revealed" is simply that screen's finished state, which is why there is no separate ceremony screen. It empties `revealedIds` the way `endRound` does, so the control window lists every team as a reveal button (`TotalGrid selectable`) while the projection starts blank and gains one card per click (`TotalGrid sorted revealing`). Each card then runs a three-beat ceremony of its own, timed from that team's click (`FINAL_*` in `projectionOrder.ts`): 0–1s it arrives glowing and showing its **gross** settled score with the penalty chip laid out but hidden; 1–3s the chip appears pulsing and the total rolls down to the net score one value at a time (`ScoreRoll.vue`); 3–5s the pulse stops, the card slides from its gross rank to its net one and the confetti fires. A team with no penalty to apply skips the middle beat and settles at `FINAL_GROSS_HOLD_MS` — the chip appears at that same instant on the teams that do have one, so the shorter timeline gives nothing away early.

**The in-round and reveal projections are one view with two populations, not two views** — the same `ScoreboardGrid` instance, showing either every player or just `revealedIds`. That is a load-bearing detail, not an optimisation: `ScoreboardCard` animates *on mount*, so remounting the grid between the two would replay every glow and confetti burst at once. Hence `ProjectionScreen` branches on `'total'` first and keeps `'round'`/`'reveal'` in the same `v-else`, and `ScoreboardGrid` passes `animate` (true only while revealing) so the cards that merely sit there — after a reload, or on the way back from the total screen — mount in silence.

Two flows are both supported and equally valid:

- **Two windows**: the operator opens the projection window on a second monitor. `MainScreen` is then purely the control surface; `ProjectionScreen` is the audience-facing display.
- **One window**: the operator never opens a second window (no second monitor, or a mirrored/duplicated display). `MainScreen` alone continues to serve as both control and projection, exactly as the app behaved before this feature — nothing about it changes.

This needed a router (`src/router/index.ts`, `vue-router`, `createWebHashHistory` — `#/projection`, chosen because GitHub Pages has no server-side SPA fallback and `base` is dynamic, see Deployment below) and split what used to be `App.vue`'s single template into: `App.vue` (a thin shell — locale mirroring, `--bg-image`/theme binding, `<router-view>` — kept here because it must apply in *every* window regardless of route), `MainScreen.vue` (the `/` route, today's former `App.vue` content unchanged), and `ProjectionScreen.vue` (the `/projection` route, gated on `game.hasPlayers`/`game.projectionScreen`).

**The order of writes inside an action is load-bearing, not cosmetic.** A projection window receives each changed localStorage key as its own `storage` event, so it renders *every intermediate combination* an action passes through — there is no batching across windows the way Vue batches within one. Two consequences are already baked into `game.ts` and must not be "tidied up":

- `endRound()` writes `revealedIds = []` → `screen = 'reveal'` → `settledRounds`, in that order. Publishing the round before the scoreboard has emptied would flash the entire round's results at the audience one event ahead of the reveal.
- `endGame()` writes `revealedIds = []` → `screen = 'total'` → `settledRounds`, and each end of that sandwich is load-bearing for its own reason. `revealedIds` first, or the total view mounts with every id still revealed (the reveal screen leaves the list full) and prints the whole podium at once. `settledRounds` **last**, or — ending from the round screen, where the projection is still on the frozen scoreboard reading `getSettledScore` — the points the operator has just tallied in private flash across every card one event before the screen turns over. By the time it lands, the total view is up and empty. Ending from the reveal screen usually writes only the first two: `max(settledRounds, currentRound + 1)` is already the current value, and a no-op assignment fires no event.
- `nextRound()` deliberately does **not** clear `revealedIds` (only `endRound` and `endGame` do). Clearing it there empties the scoreboard for the single event before `projectionScreen` turns back to `'round'`, which reads as every card blinking out and straight back in.
- Penalty writes are safe by construction, and the reasoning is worth keeping: `adjustPenalty` touches one ref (`players`), so a projection window gets a single `storage` event and no intermediate state — and on `'round'`/`'reveal'` its output is unchanged anyway, since `ScoreboardCard` reads only the two penalty-free getters. Making the total view penalty-aware likewise adds no flash to `endGame()`, which never writes `players`: the penalties are already in place when that view mounts, so its first frame is already net. One new key crosses windows, `screen-counter:penalties-enabled`, read by the projection through `TotalGrid` — toggling it flips the totals live in both windows, the same way a theme colour does.

The same hazard is why `getRevealScore` keys off `settledRounds` rather than `currentRound`. When adding an action that writes several keys, walk the intermediate states from the projection's point of view.

**The two windows are fully independent app instances** — `main.ts` runs a second time from scratch in the projection window: its own Pinia, its own `vue-i18n`, its own `document`. There is no direct communication channel between them (no `BroadcastChannel`, no shared memory, no custom event bus). All syncing is the pre-existing `useLocalStorage` + native `storage`-event mechanism already used for every other piece of persisted state — the projection feature adds no new sync machinery, only the `projectionScreen`/`revealedIds` fields a second window happens to read. One consequence worth knowing: `sanitizeState()` only runs once per store instantiation, not reactively on every incoming cross-window `storage` event — a value arriving live in an already-open window relies on write-side invariants (here, the watcher only ever writes `'total'`/`'reveal'`, and `settledRounds` is only ever written as `currentRound + 1`), not a re-validation pass.

- **`src/assets/main.css`** — the layout is the hard part of the UI, not the markup. The app is locked to the viewport (`100dvh`, `overflow: hidden`, no page scroll). Sizing is almost entirely `vmax` / `clamp(px, vmax, px)` so it scales with the larger screen dimension for across-the-room readability. **No card layout is a CSS grid, on purpose**: a grid packs a partial last row to the start, so five teams would sit 3 + 2 hugging the left edge. `.score-grid` (control tally/reveal screens and both total views) and `.scoreboard-grid` (projection scoreboard) are one shared set of rules — a centred `flex-wrap` flow (`justify-content`/`align-content: center`) whose *children* carry the count: the store exposes `gridMajor`/`gridMinor` (larger/smaller axis, from `rows = ceil(sqrt(n/2))`, `cols = ceil(n/rows)`), `ScoreGrid.vue`/`TotalGrid.vue`/`ScoreboardGrid.vue` pass them as `--grid-major`/`--grid-minor` inline styles, and each card takes `width: calc((100% - gap * (major - 1)) / major)` and the matching height from minor, swapped under `@media (orientation: portrait)` so the larger axis runs down the screen. The wrap then breaks after exactly `major` cards, every card stays inside the locked viewport with no scroll (large player counts shrink the cards rather than overflow), an incomplete last line is centred, and — because the size comes from the *roster* rather than from how many cards are currently shown — a card is exactly the same size whether the scoreboard holds one revealed team or all of them. Card text tracks the card box, not the viewport: `.score-card` is a `container-type: size` query container and its text (`.round-score`, `h3`, `.total-score`, `.grand-total`, etc.) is sized in unclamped `cqmin` units, so it stays proportional as cards shrink and in both orientations. Everything outside the cards still uses `vmax` / `clamp()`; new UI must follow suit — no `rem`. Because the viewport is locked, `.setup-panel` and `.settings-panel` are the only panels allowed `overflow: auto`, since their content is a list that legitimately outgrows a short screen. The total screen's per-round breakdown (`.round-list`) is the same centred wrap one level down — a value-only flow whose chips are sized from `--round-major`/`--round-minor` (computed by `TotalGrid` itself via `splitGrid` in `src/lib/grid.ts`, transposed in portrait — **not** from the store, because the cell count is one per settled round *plus* the optional penalty chip, and whether that chip shows depends on a setting `game.ts` deliberately knows nothing about; `.round-list` clips its overflow, so a split sized for the rounds alone drops the chip silently rather than spilling it) off its own `--round-gap`; each `.round-item` is its own `container-type: size` container so the digit fills its cell in `cqmin` and shrinks automatically as rounds accumulate — every round stays visible, never clipped. `App.vue` sets the background image via a `--bg-image` CSS custom property inline, and the theme overrides ride along the same way (below). The typeface is `--app-font`, defaulted in `:root` and consumed by `.app` as `font-family: var(--app-font), sans-serif` — that declaration is what makes the font themeable at all, since `base.css` puts its stack on `body`, a *parent* of `.app` and so out of reach of the inline overrides; the trailing `sans-serif` is the last resort when a chosen family is not installed. Controls inherit it for free from the existing `font: inherit` rules. `.score-controls` uses `grid-auto-rows: 1fr` rather than fixed tracks, because it holds two buttons or four depending on the penalties setting — explicit tracks would leave empty rows and half-height +/− buttons whenever it is off; `.score-controls--penalty` exists only to shrink the glyph when four rows halve each button's height, and again in portrait, where `cqmin` tracks the card's width while the rows divide its height. `--penalty-text` joins `--button-bg-hover` and friends in the derived-from-the-palette group in `:root`, so the single "Penalty buttons" picker (the `negative` theme key, dead until this feature) themes the control pair, the card's red annotation and the breakdown chip together. `.score-card--readonly` (cards with no +/− buttons: every projection card, and the control's cards once the round is closed) collapses the column normally reserved for `.score-controls`; `.round-panel.no-header`/`.total-panel.no-header` (set by `ProjectionScreen`) collapse the header's grid row so the score grid alone fills the panel. `.scoreboard-grid` adds nothing to the shared layout above but `--confetti-delay`: the centring it already has is what lands the first revealed card dead centre, and the roster-based card size is what keeps it from resizing as the reveal fills up. The end-of-game ceremony adds four things to the same file, all of them reusing what is already there: `.score-order-enter-*`/`-leave-*` (the total grid declared only `-move` until that screen became a reveal, so a revealed card would have popped in — a `TransitionGroup` does not run enter transitions on its own initial mount, so an already-full board still renders in one silent shot); `.round-item--pending`, which is `visibility: hidden` rather than `opacity: 0` so the chip holds its cell in the centred `.round-list` wrap without shoving the round chips sideways when it appears; `.round-item--pulsing`, whose period is **CSS-only on purpose** because the animation is `infinite` and JS decides when it stops, so there is no constant to keep in lockstep; and `.score-roll*`, whose line box is expressed in `em` off `.grand-total`'s `24cqmin` — deliberately not `translateY(-100%)`, since a percentage translate resolves against the track's own height and the track is every line tall.

The rest is the theming feature:

- **`src/stores/settings.ts`** — appearance, language and the one gameplay switch (background image, theme, font, `locale`, `penaltiesEnabled`), deliberately a **separate** Pinia store from `game.ts` so it never mixes with players and scores. `penaltiesEnabled` lives here rather than in `game.ts` for the same reason `locale` does: it is an operator preference that has to survive `startGame`, and `game.ts` is the state machine, not the preference store. It **defaults to on** — an opt-out, not an opt-in — so an operator who wants penalties never has to find the setting first; note the asymmetry that leaves in `sanitizeSettings`, where a *corrupt* persisted value lands on off rather than back on the default, which is the safe direction (show the totals the scores add up to rather than silently deducting). It follows the scalar pattern `locale`/`font` set — its own `useLocalStorage`, a line in `sanitizeSettings`, a setter, an entry in the returned object — and is deliberately **not** a `THEME_FIELDS` key, since it is a boolean rather than a colour. The game store stays ignorant of it: `getFinalScore` always subtracts, and the two components gate the UI. `DEFAULT_THEME` mirrors the palette `main.css` ships in `:root`, so an untouched theme renders identically to before the feature existed. `sanitizeSettings()` mirrors `sanitizeState()`: it rebuilds the theme from `DEFAULT_THEME` (dropping unknown keys from older persisted shapes), falls back per-key on anything `parseColor` rejects, and resets `locale` (`screen-counter:locale`) to `detectBrowserLocale()` when the persisted value is not a `SUPPORTED_LOCALES` member. `locale`'s `useLocalStorage` default is `detectBrowserLocale()`, so the browser language applies until the user picks one on the settings screen; `App.vue` mirrors `settings.locale` onto the `vue-i18n` instance and `document.documentElement.lang` in a `watchEffect`. The `cssVars` getter maps theme keys to the `--app-text` / `--overlay` / … custom property names, and `App.vue` spreads it into the same inline `:style` on `.app` as `--bg-image` — which is why the theme also applies to the settings screen itself, giving a live preview. The font (`screen-counter:font`) is a **scalar setting alongside the theme, not a key inside it** — modeled on `locale`, because a font is not a color and would only fight `parseColor` and the one-`ColorPicker`-per-`THEME_FIELDS` loop. `DEFAULT_FONT` mirrors the `--app-font` default in `:root` for the same reason `DEFAULT_THEME` mirrors the palette, `sanitizeSettings()` repairs it through `normalizeFontFamily` (falling back to `DEFAULT_FONT`), and `cssVars` adds `--app-font` after the theme reduce, so it reaches both windows with no change to `App.vue`. `resetFont()` is deliberately separate from `resetTheme()`: "Reset theme" must not silently change the typeface. Adding a themeable **color** means touching four places in lockstep: `DEFAULT_THEME`, `THEME_FIELDS` (the ordered `ThemeKey[]` that drives the settings UI), `THEME_CSS_VARS`, and the `:root` default in `main.css` — plus a matching `settings.theme.fields.<key>` string in **both** locale catalogs, since `themeFieldLabelKey(key)` derives the i18n key from the theme key.
- **`src/i18n/`** — `locale.ts` is pure (`SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`, `detectBrowserLocale`, `isSupportedLocale`) with no `vue-i18n` import, so `settings.ts` can use it without pulling in the i18n runtime. `index.ts` builds the `createI18n` instance (`legacy: false`) from the YAML catalogs. **All user-facing strings live in `src/i18n/locales/{en,fr}.yaml`** — `@intlify/unplugin-vue-i18n` (wired in `vite.config.ts`) precompiles them at build time, so the runtime-only `vue-i18n` build is enough. `env.d.ts` declares the `*.yaml` module for `vue-tsc`. Every screen component resolves strings through its own `t()` (each installs its own `useI18n({ useScope: 'global' })`, since screens now live in separate components); `ColorPicker.vue` stays i18n-agnostic (it receives an already-resolved `label` string), but `FontPicker.vue` does **not** — it needs a label, a placeholder, a button, a hint and two error states, and threading five resolved strings through props would be worse than the `useI18n` the screens already install.
- **`src/lib/color.ts`**, **`src/lib/font.ts`**, **`src/lib/grid.ts`**, **`src/lib/backgroundImage.ts`** and **`src/lib/localFonts.ts`** — pure/DOM helpers kept out of the stores so the stores stay free of DOM APIs (`FileReader`, `Image`, canvas) and stay testable. `parseColor` returns `null` rather than a fallback so callers own the default. `grid.ts` holds `splitGrid`, which used to live inside the game store; it moved out so both the store (player cards, from the roster) and `TotalGrid` (the breakdown, whose cell count depends on a setting the store must not know) can call the same function. `fileToBackgroundDataUrl` downscales anything over 3 MB to a JPEG so the base64 string stays inside the localStorage quota. `normalizeFontFamily` follows `parseColor`’s contract (`null`, not a fallback) and validates against a **whitelist** rather than a blacklist, because the value ends up in a CSS custom property that `font-family` consumes — it also normalizes (quoting names with spaces, leaving generic families and `-apple-system`-style identifiers bare), so a value round-trips through localStorage unchanged. `localFonts.ts` wraps the Local Font Access API: `queryLocalFonts()` is Chromium-only and needs a secure context plus transient user activation, so it must be called straight from a click handler, and it throws a `LocalFontsError` carrying a typed `reason` (`unsupported` / `denied` / `failed`) so the caller picks an i18n key instead of matching on an English message.
- **`src/components/`** — `MainScreen.vue` (the `/` route: setup/round/reveal/total/settings) and `ProjectionScreen.vue` (the `/projection` route, see "Projection window" above) render player cards through **two separate families, split by window rather than by screen**. Control window: `ScoreGrid.vue` → `ScoreCard.vue`, always in roster order (the operator's cards must never move under their finger) and never animated; its `mode` prop (`'tally' | 'reveal'`) swaps the +/− controls for a whole-card reveal button and swaps `getTotalScore` for `getSettledScore`. In `tally` mode with penalties on it carries **three** numbers and **four** controls: the round draft, the still-gross total, a red penalty annotation beside it, and a second +/− pair below the first. Both pairs use the same two glyphs, so colour and the heavier rule between them are the only visual difference — which is what makes all four `aria-label`s load-bearing rather than decoration. The `reveal` card stays deliberately penalty-free: it shows exactly the pair of numbers the audience is about to see. Projection window: `ScoreboardGrid.vue` → `ScoreboardCard.vue`, sorted and animated, covering both the in-round and reveal states (above). `TotalGrid.vue` → `TotalCard.vue` (→ `ScoreRoll.vue`) is the projection's end-of-game view and the control's total screen — the only place the per-round breakdown is shown at all, and, being the end of the game, the only view where penalties apply, as a red chip after the round chips and as the **net** total it both prints and ranks by — through `sortByFinalScore` rather than the scoreboard's `sortByTotalScore`, because a tie on the net is broken by the **smaller** penalty (37−7 and 38−8 both come to 30, and the team that lost less to penalties places higher). Both keys are read at the card's current phase, so a team still mid-ceremony ties as though it had no penalty: ranking it by a deduction the audience has not been shown yet would seat it low with nothing to explain why. Because that screen is also the end-of-game reveal, it has two populations the way `ScoreboardGrid` does, and **three independent props named for what they do rather than for the window that sets them**: `sorted` (rank the cards), `revealing` (population = `revealedIds`, run the ceremony clock) and `selectable` (the whole card is a reveal button, already-revealed ones dimmed). Only two combinations exist today — `<TotalGrid selectable />` on the control and `<TotalGrid sorted revealing />` on the projection — but keeping them separate is what stops a future "sort the control window too" from silently switching the buttons off. `TotalCard` takes its numbers already resolved (`roundScores`, `penalty`), so whether penalties are enabled at all stays `TotalGrid`'s business and `penalty === 0` simply means "no chip". All of them read `useGameStore()` directly rather than taking it as a prop; `ScoreCard` and `TotalGrid` read `useSettingsStore()` the same way, to gate the penalty UI.
  - **The round reveal's animation lives in `ScoreboardCard` alone, and fires on mount, not on change.** A revealed card appears exactly once, already carrying its result, so there is nothing to diff: `onMounted` puts the glow class on (positive/negative by the sign of the round's points, nothing at all for zero, nothing at all when `animate` is false) and drops it after `REVEAL_HIGHLIGHT_HOLD_MS`. The sequence reads glow → placement (`.scoreboard-enter-*` on the newcomer, `.scoreboard-move` on the cards sliding aside) → confetti (CSS `animation-delay`, held back by `--confetti-delay` until the placement has settled) → both fade out, the last step being the `box-shadow` transition on `.score-card`. Every duration is declared twice, in `src/lib/projectionOrder.ts` and in `main.css`; they must be changed in lockstep.
  - **The end-of-game ceremony's clock is the one deliberate exception: it lives in `TotalGrid`, not in `TotalCard`.** The reorder is a *grid* concern — a freshly revealed team is ranked by its gross score until the penalty lands and by its net score after, and that late switch of the sort key is exactly what makes the card slide down past the teams it no longer beats. So the grid keeps a per-id `'enter' | 'penalty' | 'settled'` map, seeded **synchronously at setup** (ids already revealed when it mounts — a reload, or a projection window opened mid-ceremony — start settled and therefore silent), with `'enter'` as the fallback for anything that arrives later, so a new id is in its opening phase on the first render that contains it no matter when the watcher runs. The card still owns everything local to itself, and its confetti is keyed off the *transition* into `'settled'` rather than the value, which is `animate`'s analogue: a card that mounts settled has no transition to see. `ScoreRoll.vue` is the odometer, and it is timed by a **CSS transition, not JS** — a transition never fires for a value present at first paint, so every "should be silent" case (reload, control window) is silent by construction rather than by a flag. It stays mounted in every mode and is re-keyed on `gross`-`net`, so toggling the penalties setting while the board is up snaps instead of scrolling. `ColorPicker.vue` is unrelated to any of this: native `<input type="color">` plus an opacity `<input type="range">`, because `<input type="color">` cannot carry alpha and most of the palette is `rgba()` — both inputs rebuild a full `Rgba` from the current value before emitting, so editing the hue keeps the alpha and vice versa. `FontPicker.vue` sits beside it on the settings screen and follows the same emit-only contract, with two deliberate differences. It **commits on `change`, not `input`**: the text input carries a local draft, because writing every keystroke to the store would restyle both windows while a half-typed name matches nothing — only the live preview tracks the draft. And its list of installed families is **rendered rows, not a `<datalist>`**, so each row can be drawn in its own font (the point when hunting for one particular face); the same input doubles as the list filter. The browse button only exists where `canQueryLocalFonts()` is true, and a translated note replaces it everywhere else — free text is the whole feature outside Chromium. Note for tests: `@vue/test-utils`’ `setValue()` fires `input` **and** `change` (for `v-model.lazy`), i.e. a commit — to model typing, set `element.value` and trigger `input` alone.

`App.vue` is presentational infrastructure shared by both routes (locale mirroring, background/theme styling, `<router-view>`) — it no longer contains any screen markup itself; see "Projection window" above for where that went. `src/main.ts` is boilerplate (Pinia + router + i18n + mount).

## Deployment

`.github/workflows/deploy-pages.yml` builds and deploys to GitHub Pages on every push to `main`. `vite.config.ts` derives `base` from `GITHUB_REPOSITORY` when running in Actions (so it serves correctly from `/<repo>/`), and `/` otherwise.

## Conventions

- `@` path alias → `src/`.
- Lint scripts always pass `--fix`; run `npm run lint` and let it rewrite rather than hand-fixing style.
- Store tests (`src/stores/__tests__/*.spec.ts`) clear `localStorage` and call `setActivePinia(createPinia())` in `beforeEach`; persistence is tested by re-creating the pinia instance and reading state back. `useLocalStorage` keeps string refs **raw**, so seed them with `setItem(key, 'settings')`, never `JSON.stringify`.
- Specs must live in a `__tests__` directory: `tsconfig.app.json` excludes that path, `tsconfig.vitest.json` includes it, and `eslint.config.ts` scopes the vitest rules to it. `tsconfig.vitest.json` sets `lib: []`, so newer built-ins (e.g. `Array.prototype.at`) are not typed in tests even though they run fine.
- Vitest `globals` is off — import `describe`/`it`/`expect` explicitly.
